``cuda.core`` 1.3.0 Release Notes
==================================

Highlights
----------

- ``cuda.core`` now requires ``cuda-bindings`` 12.9.8 or newer for CUDA 12, and 13.5.0 or newer
  for CUDA 13. With an older ``cuda-bindings``, ``import cuda.core`` fails with a message that
  names the required version. ``pip install 'cuda-core[cu12]'`` or ``pip install 'cuda-core[cu13]'``
  installs a compatible version. See the :ref:`support policy <cuda-core-bindings-floor>`.
  (`#2783 <https://github.com/NVIDIA/cuda-python/issues/2783>`__)

- Support for Python 3.10 is dropped (end of life).

- :class:`VirtualMemoryResource` buffers can be shared with other processes through POSIX file
  descriptors or fabric handles.

- :func:`host_launch` enqueues a Python callable or a compiled host function on a stream in
  stream order.

- A new :doc:`error handling <../error_handling>` policy: :class:`CUDAWarning` reports CUDA
  errors that cannot be raised, and :class:`CUDAOutOfMemoryError` is a :class:`MemoryError`.

New features
------------

- Added read-only ``GraphDefinition.id``, ``Graph.id``, ``GraphNode.local_id``
  and ``GraphNode.tools_id`` properties (CUDA 13 build and driver 13.1+), and
  ``KernelAttributes.device_node_update_supported`` (CUDA 13 build and driver 13.3+).
  The existing ``GraphNode.graph`` property provides containing-graph navigation.
  (`#2360 <https://github.com/NVIDIA/cuda-python/issues/2360>`__)

- Added :func:`host_launch`, which enqueues a host function on a stream in stream
  order: a Python callable, or a ctypes function pointer with the ``CUhostFn``
  prototype, which ``cuda.core`` passes to the driver as is, so a pointer to
  compiled code runs without the GIL. It is the stream-side counterpart of
  :meth:`graph.GraphBuilder.callback` and accepts the same ``fn`` and
  ``user_data`` forms.
  (`#2058 <https://github.com/NVIDIA/cuda-python/issues/2058>`__)

- Added :data:`HOST_COPY_FN`, a host function that copies host memory without
  the GIL, and :func:`pack_host_copy_args`, which packs its ``user_data``. Pass
  both to :func:`host_launch` or a graph host callback method for a host copy
  in stream order, for example from a pinned staging buffer into a NumPy array,
  without a compiled extension of your own.
  (`#3256 <https://github.com/NVIDIA/cuda-python/issues/3256>`__)

- Added incremental linking to :class:`Linker` through
  ``LinkerOptions(incremental=True)`` on nvJitLink 13.2 or newer. A partial
  native result is returned as a CUBIN and can be passed directly to another
  linker. :meth:`Linker.link` also accepts ``"ltoir"`` on nvJitLink 13.3 or
  newer so incremental LTO chains can retain IR until their final link. Direct
  PTX and CUBIN inputs are rejected for this target because they carry no LTOIR
  and nvJitLink would otherwise silently omit them. On nvJitLink versions
  older than 13.6, incremental links with link-time optimization disable the
  nvJitLink intermediate cache, which crashed after repeated links on Windows.
  (`#2369 <https://github.com/NVIDIA/cuda-python/issues/2369>`__,
  `#3038 <https://github.com/NVIDIA/cuda-python/issues/3038>`__)

- Added the ``priority`` option to :class:`LaunchConfig`, which sets the
  execution priority of a kernel launch. Lower numbers are higher priorities.
  The valid range is the device's stream priority range, as for
  :attr:`StreamOptions.priority`. A nonzero value outside it raises
  ``ValueError``. The default, ``0``, leaves the stream's priority in effect.
  (`#2631 <https://github.com/NVIDIA/cuda-python/issues/2631>`__)

- Added the ``cluster_scheduling_policy_preference`` option to
  :class:`LaunchConfig`: ``"DEFAULT"``, ``"SPREAD"``, or
  ``"LOAD_BALANCING"``. It requires compute capability 9.0 or newer.
  (`#2629 <https://github.com/NVIDIA/cuda-python/issues/2629>`__)

- Added the read-only :attr:`ManagedBuffer.last_prefetch_location` property,
  which reports the destination requested by the most recent explicit
  prefetch across the buffer. It returns a :class:`Device` or :class:`Host`,
  including NUMA-specific host locations on CUDA 13, and ``None`` if any page
  has never been prefetched or the pages do not share one last-prefetch
  location. This reports the requested target, not current residency or
  completion of the asynchronous prefetch operation.
  (`#2109 <https://github.com/NVIDIA/cuda-python/issues/2109>`__)

- Added :class:`CUDAWarning`, the warning category ``cuda.core`` uses for CUDA
  errors that cannot be raised, such as a failed driver call while a resource
  is released by the garbage collector. Filter on it with
  ``warnings.filterwarnings("error", category=cuda.core.CUDAWarning)`` to make
  such failures loud. The new :doc:`error handling <../error_handling>` page
  documents what an exception from ``cuda.core`` guarantees, how failures that
  cannot be raised are reported, and how context restoration failures and
  sticky CUDA errors are handled.

- :class:`CUDAError` and :class:`NVRTCError` are now importable from the
  top-level ``cuda.core`` namespace, alongside :class:`CUDAWarning`. Previously
  they were only available from a private module.

- The memory pool attributes of :class:`DeviceMemoryResource`,
  :class:`PinnedMemoryResource` and :class:`ManagedMemoryResource` can now be
  set: ``release_threshold`` takes a non-negative integer, the three
  ``reuse_*`` policies take a bool, and ``reserved_mem_high`` and
  ``used_mem_high`` can be set to zero to reset the watermark, as for
  :class:`GraphMemoryResource`. The new :meth:`DeviceMemoryResource.trim`
  method, also on the other two resources, returns unused pool memory to the
  OS. Setting an attribute and ``trim()`` take effect immediately, even during
  a stream capture, and leave the capture valid.
  (`#3261 <https://github.com/NVIDIA/cuda-python/issues/3261>`__)

- Added :class:`CUDAOutOfMemoryError`, raised for ``CUDA_ERROR_OUT_OF_MEMORY``
  and ``cudaErrorMemoryAllocation``. It derives from both :class:`CUDAError`
  and :class:`MemoryError`, so ``except MemoryError`` catches an allocation
  that fails in ``cuda.core`` as it does in CuPy, RMM and NumPy. Code that
  catches :class:`CUDAError` is unaffected.

- Added :class:`VirtualMemoryBuffer`, the :class:`Buffer` subclass that
  :class:`VirtualMemoryResource` returns. Closing it on a capturing stream
  other than a default stream raises, because virtual memory deallocation
  cannot be captured. A release ordered on a default stream that would
  disturb a capture in its context is reported as a :class:`CUDAWarning`
  and proceeds without the synchronization.

- :class:`VirtualMemoryResource` buffers can now be shared with other
  processes the way pool-backed buffers are, through two transports chosen
  by the resource's ``handle_type``. :attr:`Buffer.ipc_descriptor` exports
  every physical allocation that backs a :class:`VirtualMemoryBuffer`,
  :meth:`Buffer.from_ipc_descriptor` imports the descriptor with a
  ``VirtualMemoryResource`` of the receiving process for the device that owns
  the memory, and :attr:`VirtualMemoryResource.is_ipc_enabled` is ``True``
  when ``handle_type`` is ``"posix_fd"`` or ``"fabric"`` on Linux and the
  memory lives on a device; host-located virtual memory is not shared yet. A
  grown buffer imports as one contiguous range, and a buffer that contains
  imported memory cannot be exported again.

  With ``"posix_fd"``, each allocation is exported as a POSIX file
  descriptor; a buffer or its descriptor travels through ``multiprocessing``
  directly (plain ``pickle`` cannot carry file descriptors). The descriptor
  holds one file descriptor per physical allocation and pins the memory while
  it exists; nothing else does. For a transport of your own, it exposes
  ``fds``, ``sizes``, and ``size``, and
  ``VirtualMemoryFdBufferDescriptor.from_fds()`` rebuilds it in the receiver.

  With ``"fabric"``, each allocation is exported as a 64-byte fabric handle;
  the descriptor is plain data that ``pickle`` carries, and it pins nothing:
  keep the exporting buffer alive until every importer has imported it.
  ``VirtualMemoryFabricBufferDescriptor.from_handles()`` rebuilds a descriptor
  received through a transport of your own. Sharing is supported on one node;
  multi-node sharing is untested. Fabric requires an NVLink fabric and an
  accessible IMEX channel (``/dev/nvidia-caps-imex-channels/channel*``);
  resource construction raises ``RuntimeError`` when the device reports no
  fabric handle support. A device can report support while the allocation is
  refused, because the attribute does not check for an NVLink fabric and
  older drivers do not check for an IMEX channel; the allocation then fails
  with a driver error that says so. Fabric-handle sharing was
  validated on NVIDIA internal hardware and is not covered by the project's
  CI in this release.
  (`#2980 <https://github.com/NVIDIA/cuda-python/issues/2980>`__)

Fixes and enhancements
----------------------

- :meth:`utils.StridedMemoryView.from_dlpack` and
  :meth:`utils.StridedMemoryView.from_array_interface` use the stable C API of
  PyTorch 2.14 and newer for PyTorch tensors, and no longer cap the supported
  PyTorch version. PyTorch 2.3 to 2.13 keep the previous path.
  (`#3033 <https://github.com/NVIDIA/cuda-python/pull/3033>`__)

- Kernels can read and write :class:`PinnedMemoryResource` buffers. The driver
  makes a host memory pool accessible only from the host by default, so a
  kernel that touched such a buffer failed with ``CUDA_ERROR_ILLEGAL_ADDRESS``.
  The resource now grants the device that is current when it is created read
  and write access to the pool.
  (`#3205 <https://github.com/NVIDIA/cuda-python/issues/3205>`__)

- ``register()`` on a :class:`~_memory.DeviceMemoryResource` or a
  :class:`PinnedMemoryResource` now raises ``ValueError`` when the resource
  already has a different UUID. The check used to be an ``assert``, so under
  ``python -O`` a mismatched UUID silently rewrote the resource's UUID and
  corrupted the IPC registry.
  (`#2697 <https://github.com/NVIDIA/cuda-python/issues/2697>`__)

- A :class:`~_memory.DeviceMemoryResource` or a :class:`VirtualMemoryResource`
  sent through ``multiprocessing`` now names its device, and the
  ``VirtualMemoryResource`` ``peers``, by UUID. The receiving process maps
  each UUID to its own device ordinal. Before, the receiver used the sender's
  ordinals, which name different devices when ``CUDA_VISIBLE_DEVICES``
  differs between the processes. Unpickling now raises ``RuntimeError`` when
  one of the devices is not visible in the receiving process.
  (`#3097 <https://github.com/NVIDIA/cuda-python/issues/3097>`__)

- A pickled :class:`Device` now names its device by UUID, and unpickling
  returns the device with that UUID in the receiving process. Before, it
  named the device by ordinal, which names a different device when
  ``CUDA_VISIBLE_DEVICES`` differs between the processes. Unpickling raises
  ``RuntimeError`` when the device is not visible in the receiving process.
  The pickled form is for processes on the same machine.
  (`#3196 <https://github.com/NVIDIA/cuda-python/issues/3196>`__)

- Fixed a ``TypeError`` in :meth:`Program.compile` when retrying after PCH
  heap exhaustion.

- :meth:`Buffer.set_deallocation_stream` and :meth:`Buffer.from_handle` now raise
  :class:`MemoryError` when the host runs out of memory while binding a default
  stream, instead of aborting the process with ``std::terminate``.

- :attr:`system.Device.uuid_without_prefix` preserves UUIDs that NVML already
  reports without a prefix, such as on Orin. This also allows
  :meth:`system.Device.to_cuda_device` to match those devices correctly.
  (`#2947 <https://github.com/NVIDIA/cuda-python/pull/2947>`__)

- A :class:`Program` that is collected as part of a reference cycle no longer
  raises ``AttributeError`` from its destructor, and the source file it wrote
  for a ``debug`` or ``lineinfo`` build is removed. The cyclic collector
  clears object attributes before the destructor runs, and the destructor
  read the program options to locate that file.
  (`#2876 <https://github.com/NVIDIA/cuda-python/issues/2876>`__)

- ``Graph.__getitem__`` now declares an overload for each node type that has
  an executable view, so type checkers and editors see the precise view type:
  indexing with a :class:`~graph.KernelNode` yields an
  :class:`~graph.ExecutableKernelNode`, and so on for memset, memcpy,
  child-graph, event-record, event-wait, and host-callback nodes. Indexing
  with a node type that has no executable view is now also reported
  statically.
  (`#2482 <https://github.com/NVIDIA/cuda-python/issues/2482>`__)

- :class:`~_memory.DeviceMemoryResource` can now be constructed for a
  device's default pool (without options), and :attr:`Device.memory_resource`
  first accessed, while the calling thread is inside a ``global`` or
  ``thread_local`` stream capture. The constructor applies its
  release-threshold policy with pool attribute calls that the driver refuses
  during such a capture; it now makes them in relaxed capture mode and
  restores the thread's previous mode, so the capture stays valid. Creating a
  new pool with options during such a capture is still refused by the driver.
  (`#2834 <https://github.com/NVIDIA/cuda-python/issues/2834>`__)

- Reading the :attr:`~DeviceMemoryResource.attributes` of a
  :class:`DeviceMemoryResource`, :class:`PinnedMemoryResource` or
  :class:`ManagedMemoryResource` no longer fails, or invalidates a stream
  capture, while the calling thread is inside a ``thread_local`` capture or
  any thread is inside a ``global`` one.
  (`#3236 <https://github.com/NVIDIA/cuda-python/pull/3236>`__)

- Ending, closing, or collecting a top-level :class:`~graph.GraphBuilder`
  whose capture was invalidated, or left unjoined by a
  :meth:`~graph.GraphBuilder.join` that failed partway, no longer crashes.
  :meth:`~graph.GraphBuilder.end_building` and
  :meth:`~graph.GraphBuilder.close` end the capture and raise the driver
  error, after which the builder holds no graph. A failed ``join`` also closes
  the builders it did not join, even when closing one of them fails. This
  does not extend to the body
  builder of a conditional node: an invalidated body capture leaves the parent
  graph invalid as well, and ending it may crash the process
  (`#2918 <https://github.com/NVIDIA/cuda-python/issues/2918>`__). Calling
  ``end_building`` on a forked builder is now rejected with ``RuntimeError``;
  forked builders are ended by ``join``.
  (`#2834 <https://github.com/NVIDIA/cuda-python/issues/2834>`__,
  `#2776 <https://github.com/NVIDIA/cuda-python/issues/2776>`__)

- :class:`Device` methods that create resources or synchronize now act on that
  device's bound context, even when another device is current. They do not
  change which device is current. For example, ``dev1.sync()`` synchronizes
  device 1's bound context even when device 0 is current, and no longer
  touches other contexts on device 1 (such as a green context). :meth:`Device.set_current`
  now always returns a :class:`Context` with the correct device ID; passing a
  context created on a different device than the receiver now delegates to
  that device's own :meth:`~Device.set_current` instead of raising, so a
  context this method returns can always be pushed back through any
  :class:`Device` object.
  (`#2311 <https://github.com/NVIDIA/cuda-python/issues/2311>`__)

- :meth:`Stream.wait` given a stream now works when that stream belongs to a
  device that is not current. The temporary ordering event is created in the
  waited-on stream's context rather than the current one, which
  ``cuEventRecord`` rejects when the two differ. The stream ordering applied
  when importing foreign arrays and tensors uses the producer stream's context
  the same way.
  (`#2311 <https://github.com/NVIDIA/cuda-python/issues/2311>`__)

- :attr:`LegacyPinnedMemoryResource.device_id` now returns ``-1``, as
  documented for memory that is not bound to a device and as
  :class:`PinnedMemoryResource` already does, instead of raising
  ``RuntimeError``. :attr:`Buffer.device_id` on such a buffer returns ``-1``
  as well, which also lets a pinned buffer back a linear or pitched texture
  resource.

- Cleanup failures are now reported as :class:`CUDAWarning` instead of being
  written to ``stderr`` with ``print`` or ``fprintf``, so they can be filtered,
  captured with :func:`warnings.catch_warnings`, and escalated. Failures of
  ``cuStreamDestroy``, ``cuEventDestroy``, ``cuMemFree``, ``cuMemFreeAsync``,
  ``cuMemFreeHost``, ``cuMemPoolDestroy``, ``cuGreenCtxDestroy``,
  ``cuGraphDestroy``, ``cuGraphExecDestroy``, ``cuGraphicsUnregisterResource``,
  ``cuLinkDestroy``, ``cuArrayDestroy``, ``cuMipmappedArrayDestroy``,
  ``cuTexObjectDestroy``, ``cuSurfObjectDestroy``, user-object releases and the
  NVRTC, NVVM and nvJitLink destroy calls made from destructors were previously
  discarded; they are now reported, and each message names the failed call,
  the handle of the affected resource and the CUDA error, so Python's
  once-per-call-site warning filter does not collapse independent failures.
  ``CUDA_ERROR_DEINITIALIZED`` (the driver is shutting down) is not reported. Test code that matched the old ``stderr``
  text uses ``pytest.warns(CUDAWarning)`` instead.

- When a :class:`Device` method has to run in the device's context and the
  caller's context cannot be restored afterwards, the created resource is
  destroyed and the raised ``CUDAError`` now carries a note
  stating that the caller's context could not
  be restored and which context is current. Previously the error named only
  the driver status of the failed ``cuCtxSetCurrent`` call. If the call itself
  failed as well, its error is raised and the restoration failure is the note.
  A restoration failure during resource cleanup is reported as
  :class:`CUDAWarning`.

- Updating a memcpy or memset graph node whose context differs from the current
  one no longer risks a dangling node parameter when the caller's context
  cannot be restored after the update: the resources referenced by the new
  parameters are now retained before the restoration failure is raised.

- :meth:`Device.set_current` with an explicit :class:`Context` now switches
  contexts with a single driver call, so a failure leaves the previous context
  current instead of leaving the thread with no context. It also works when no
  context is current, returning ``None``.

- A failed rollback of a partially embedded child graph node is now attached
  as a note to the exception that triggered the rollback, and a failed ``cuStreamEndCapture``
  made when a still-building :class:`~graph.GraphBuilder` is garbage collected
  is now reported as :class:`CUDAWarning`; both were silent.

- :attr:`Stream.device` and related queries on a stream whose context is not
  current now restore the caller's context even when the device query fails.

- Closing a :class:`DeviceMemoryResource` now revokes the peer access it
  granted before the driver destroys the pool. The revocation used to be one
  request that named every device, including the pool's own; the driver
  rejects such a request as a whole, so it never took effect and a pool
  created later could inherit that access through a recycled handle. Each
  device is now revoked with its own request, so no single device can block
  the others.
  (`#2807 <https://github.com/NVIDIA/cuda-python/issues/2807>`__)

- Calling ``discard()`` on the set-like :attr:`graph.GraphNode.pred` and
  :attr:`graph.GraphNode.succ` views with an object that is not a
  :class:`~graph.GraphNode` is now a no-op instead of raising ``TypeError``,
  consistent with :class:`collections.abc.MutableSet` semantics.

- :class:`VirtualMemoryResource` now holds each physical allocation, address
  reservation and mapping in a reference-counted handle, so everything a
  buffer maps is released when the last buffer that maps it closes. The
  physical memory was leaked on every ``allocate()`` and grow
  (`#2344 <https://github.com/NVIDIA/cuda-python/issues/2344>`__), the address
  range added by an in-place grow could not be freed
  (`#2887 <https://github.com/NVIDIA/cuda-python/issues/2887>`__), a second
  grow of a buffer failed
  (`#2908 <https://github.com/NVIDIA/cuda-python/issues/2908>`__), an
  unaligned grow recorded a size the driver rejects at close
  (`#2907 <https://github.com/NVIDIA/cuda-python/issues/2907>`__), and a
  buffer was unmapped without waiting for the work queued on its stream
  (`#2886 <https://github.com/NVIDIA/cuda-python/issues/2886>`__). No
  reservation is freed by hand any more
  (`#2345 <https://github.com/NVIDIA/cuda-python/issues/2345>`__,
  `#2388 <https://github.com/NVIDIA/cuda-python/issues/2388>`__). The
  behavior of the resource changes as follows.
  :meth:`VirtualMemoryResource.modify_allocation` returns a new
  :class:`VirtualMemoryBuffer` and leaves the buffer passed in open; the two
  alias the same physical memory, which is freed when the last of them closes,
  and the pointer is preserved when the driver grants the adjacent address
  range. The result is always a new buffer, so closing it never closes the
  buffer passed in; a request the buffer already covers returns a full alias
  without a driver call, and
  :attr:`Buffer.size` after a grow is the aligned total. The ``config``
  argument applies to the chunk that call adds and is no longer stored on the
  resource (`#2909 <https://github.com/NVIDIA/cuda-python/issues/2909>`__);
  it must keep the resource's location and ``handle_type`` and passes the
  constructor's option checks. Every chunk of a buffer must be exportable
  the same way, so a resource created with ``handle_type=None`` needs
  ``handle_type=None`` in a per-call ``config`` as well. It never changes
  the access of memory that is already mapped, so a
  request the buffer already covers has no effect even with ``config``.
  Buffers from ``allocate()`` free themselves when they close and no longer
  call :meth:`VirtualMemoryResource.deallocate`, which now serves pointers
  wrapped with :meth:`Buffer.from_handle`. A buffer records the stream passed
  to ``allocate()``, and closing it waits for the work queued on that stream
  before it unmaps, because ``cuMemUnmap`` is not stream-ordered; close the
  buffer explicitly, or record an idle deallocation stream, to control when
  that wait happens. ``modify_allocation`` accepts only buffers
  this resource returned. ``location_type="host"`` requires
  ``handle_type=None``, which the driver requires. ``allocate(0)`` returns an
  empty buffer without a driver call.

- The ``StridedMemoryView`` DLPack C exchange API now preserves the underlying
  Python exception when an export or import fails, as required by the DLPack
  contract, instead of returning ``-1`` with no exception set.

- A view created with :meth:`~utils.StridedMemoryView.view` from a
  ``StridedMemoryView`` imported through DLPack now keeps the imported
  tensor alive. Previously, releasing the original view invoked the DLPack
  deleter while the derived view still referenced the memory, which could
  free a producer's temporary allocation too early.

- :meth:`~graph.MemcpyNode.update` and the executable view of a memcpy node
  now accept nodes recorded by stream capture. The driver stores the operands
  of a captured :meth:`Buffer.copy_from` or :meth:`Buffer.copy_to` as unified
  addresses, and ``update`` rejected that descriptor with a message about
  multidimensional copies. Such an operand stays unified when it is replaced,
  because the driver does not accept a change of an operand's memory type in
  an instantiated graph. Replacing a device operand with another device
  buffer of the same kind can therefore also be applied with
  :meth:`~graph.Graph.update`. Replacing it with host memory, or with memory
  from a different allocator, always takes effect in a new instantiation;
  whether an executable update accepts it depends on how the operands were
  allocated and on the driver. The driver compares the memory class of
  pool-backed and virtual-memory operands and rejects the change for them,
  while operands from plain ``cuMemAlloc`` allocations accept it. The node's
  ``repr`` now shows ``U`` for unified operands.
  (`#2649 <https://github.com/NVIDIA/cuda-python/issues/2649>`__)

- :class:`VirtualMemoryResourceOptions` rejects ``allocation_type="managed"``
  with ``ValueError`` as ``cuMemCreate`` only supports
  pinned allocations. Use :class:`ManagedMemoryResource` for managed memory.
  (`#2910 <https://github.com/NVIDIA/cuda-python/issues/2910>`__)

- The default :class:`VirtualMemoryResourceOptions` ``handle_type`` on Windows
  is now ``None``, avoiding the unsupported POSIX descriptor; Linux keeps its ``"posix_fd"`` default.
  (`#2910 <https://github.com/NVIDIA/cuda-python/issues/2910>`__)

- :class:`VirtualMemoryResource` can now allocate with
  ``location_type="host_numa"``. Every such allocation failed with
  ``CUDA_ERROR_INVALID_VALUE``, because the driver received ``-1`` as the NUMA
  node. :class:`VirtualMemoryResourceOptions` has a new ``numa_id`` field that
  names the node. It is required for ``"host_numa"`` and rejected for every
  other location type; ``Device.properties.host_numa_id`` gives the node
  closest to a device. ``location_type="host_numa_current"`` now raises
  ``ValueError`` at construction, because the driver does not accept it for
  physical allocations.
  (`#2694 <https://github.com/NVIDIA/cuda-python/issues/2694>`__)

- Checks that were ``assert`` statements now raise exceptions, so they also
  run under ``python -O``, which strips asserts from Python and Cython code.
  :meth:`~utils.StridedMemoryView.from_dlpack` raises ``ValueError`` when
  ``__dlpack_device__()`` reports a negative device ID for a CUDA tensor or a
  nonzero one for a CPU tensor, or when ``__dlpack__()`` returns anything
  other than an unconsumed DLPack capsule.
  :meth:`~utils.StridedMemoryView.from_cuda_array_interface` raises
  ``ValueError`` when the producer's ``stream`` is 0 or negative.
  :meth:`ManagedMemoryResource.allocate` raises ``TypeError`` when ``stream``
  is not a :class:`Stream`. Unpickling an :class:`ObjectCode` with an unknown
  code type raises ``ValueError``, as do :class:`~system._device.FieldValue`
  and :class:`~system._system_events.SystemEvent` when the NVML data does not
  hold exactly one entry, and :attr:`system.Device.performance_state` when
  NVML reports a P-state outside 0 to 15. Before, these raised
  ``AssertionError``, or nothing under ``python -O``. A failed internal check
  now raises ``RuntimeError`` with a message that starts with "internal
  cuda.core error, please report".
  (`#3202 <https://github.com/NVIDIA/cuda-python/issues/3202>`__)

- A process that made a device current with :meth:`Device.set_current` no
  longer crashes at interpreter shutdown. The primary context was released
  from a thread-local destructor after Python had finalized.
  (`#2743 <https://github.com/NVIDIA/cuda-python/issues/2743>`__)

- :meth:`Buffer.from_ipc_descriptor` no longer deadlocks when two threads
  import IPC buffers at the same time.
  (`#2840 <https://github.com/NVIDIA/cuda-python/issues/2840>`__)

- :class:`Linker` passes boolean nvJitLink options as ``1`` or ``0``.
  Newer nvJitLink versions reject the ``true`` and ``false`` values that it
  passed before.
  (`#3254 <https://github.com/NVIDIA/cuda-python/issues/3254>`__)

- :class:`Program` with ``code_type="nvvm"`` now raises :class:`CUDAError`
  for twelve :class:`ProgramOptions` fields that libNVVM cannot use, such as
  ``pch`` and ``no_cache``. Before, they were silently ignored.
  (`#2954 <https://github.com/NVIDIA/cuda-python/issues/2954>`__,
  `#3289 <https://github.com/NVIDIA/cuda-python/pull/3289>`__)

- A new graph no longer adopts the metadata of a destroyed graph when the
  driver reuses its handle address. Cleanup of the old graph could
  invalidate the new one.

Deprecations
------------

- Two ``cuda.core.system`` exception classes were renamed so that they no longer have the same name as a Python builtin
  exception. Code that did ``from cuda.core.system import *``
  replaced the builtin ``TimeoutError`` and ``MemoryError`` in its namespace. Update code that refers to the old names:

  - ``TimeoutError`` is now ``NvmlTimeoutError``.
  - ``MemoryError`` is now ``NvmlMemoryError``.

Known issues
------------

- :class:`PinnedMemoryResource` rejects ``HOST_NUMA`` pools on CUDA 12.6 to
  12.8 drivers, although the driver supports them. This is a regression in 1.2.0.
  (`#2795 <https://github.com/NVIDIA/cuda-python/issues/2795>`__)

- :meth:`SMResource.split` with ``dry_run=True`` raises when a group requests a nonzero SM
  count, with a CUDA 13 build on a driver of 13.1 or newer.
  (`#2765 <https://github.com/NVIDIA/cuda-python/issues/2765>`__)
