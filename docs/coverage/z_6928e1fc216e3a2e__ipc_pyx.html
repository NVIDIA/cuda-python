218cdef class VirtualMemoryFdBufferDescriptor(_VirtualMemoryDescriptor): 

219 """Serializable object describing a :class:`VirtualMemoryBuffer` that can be shared between processes. 

220  

221 The descriptor holds one exported POSIX file descriptor per physical 

222 allocation that backs the buffer, in address order (``handles``, each an 

223 :class:`IPCAllocationHandle` that the descriptor owns and closes when it 

224 is released), with each allocation's size (``sizes``) and the buffer's 

225 size (``size``, which may be smaller than their sum). ``handle_type`` is 

226 ``"posix_fd"``; the rules below describe file descriptors. 

227  

228 A descriptor pins the physical memory while it exists, in every process 

229 that holds one, and nothing else does: the exporting buffer keeps no 

230 descriptor, and an imported buffer does not keep the one it came from. A 

231 descriptor parked in a ``multiprocessing`` ``Queue`` or sent to a ``Pool`` 

232 pins the memory in the sender until the receiver has unpickled it; a 

233 buffer passed as a ``Process`` argument pins it until the ``Process`` 

234 object is released, because the child receives the file descriptors when 

235 it is spawned. 

236  

237 Two transports exist. ``multiprocessing`` (a ``Queue``, a ``Pipe``, 

238 ``Process`` arguments, or a ``Pool``) pickles the descriptor, or a buffer, 

239 and duplicates the file descriptors into the receiving process; plain 

240 ``pickle`` cannot carry them and raises. A process with its own file 

241 descriptor passing sends ``fds``, ``sizes``, and ``size`` itself, and the 

242 receiver rebuilds the descriptor with :meth:`from_fds`. 

243  

244 Note 

245 ---- 

246 The sizes are controlled by the exporting peer. Receivers must treat them 

247 as untrusted and import only through :meth:`Buffer.from_ipc_descriptor`, 

248 which checks what it can and fails instead of mapping a size the driver 

249 rejects.
